## Context

`ResultSlot`（#190）把每個大型結果存進 `window.__sbr_<名稱> = { text, len, err, started, threw }`。名稱由 CLI 挑（`--large`、`storeScript` 路徑）或由頁面挑（內嵌包裝的 `SB1:BIG:<len>:<key>`）。結束時多一次 `do JavaScript` 刪除，錯誤被忽略，逾時之後不試。硬終止、取消、逾時或頁面在清除前失效時槽留在頁面。這件事不影響正確性（名稱唯一），只是頁面記憶體：長期開啟的 SPA 上反覆中斷大型讀取會累積孤兒，每個大小同結果。

限制：槽的位置是頁面的 `window`，頁面程式碼可以讀寫；所有腳本都在使用者可見範圍不宣告變數（#190）；回覆協定與往返次數不可改變（daemon 以腳本原始碼為鍵快取，#255 的往返計數測試釘住次數）。

## Goals / Non-Goals

**Goals**

- 有界回收：孤兒不會永遠累積。
- 不傷進行中的呼叫，包括分塊長讀取與並行呼叫。
- 零額外往返；失敗時只是不回收，絕不讀到錯的資料。
- 公開實際可保證的生命週期限制。

**Non-Goals**

- 不保證「一定回收」，沒有頁面內計時器，沒有 CLI 端日誌，不依筆數上限（見 proposal 的 Non-Goals 與理由）。

## Decisions

**D1：最後使用時間 `u`，不是建立時間。** 分塊長讀取可能跨很多次往返；以建立時間判斷會刪到仍在讀的槽。每次讀取更新 `u`，所以「活著」的定義是「最近一次往返在期限內」。

**D2：回收發生在建立新槽時。** 掃描接在既有腳本裡（`presetScript`、`storeScript`、內嵌包裝的 `SB1:BIG` 分支），所以零額外往返，也不需要 CLI 記得什麼。代價：沒有後續大型呼叫就沒有回收（寫進規格的限制）。

**D3：保留期限 10 分鐘（`ResultSlot.retentionMilliseconds = 600_000`）。** 往返間隔是亞秒；10 分鐘遠大於任何正常呼叫的往返間隔，又短到 SPA 不會長期背著孤兒。唯一會被誤刪的是「同一個呼叫在兩次往返之間停滯超過 10 分鐘」（例如機器睡眠）；那時它讀槽得到既有的「傳輸不完整」錯誤，或 `--large` 的進度為 `gone` 而報「無法得知程式碼是否執行」，兩者都失敗關閉，不會重跑程式碼，也不會讀到錯的資料。

**D4：掃描條件是三個都成立才刪**：屬性名以 `__sbr_` 開頭、值是物件且 `typeof u === 'number'`、`u < now - 期限`。沒有 `u`（舊版 CLI 的槽）、`u` 不是數字、屬性不以前綴開頭，一律不動。前綴是這個 CLI 的約定，不是安全邊界（槽名本來就不是秘密，#190）。

**D5：頁面時鐘讀不到時不回收，往前跳時會提早回收。** 時鐘必須是有限數字（`typeof n === 'number' && n - n === 0`；只靠 `n === n` 擋不住 `Infinity`，那會讓每個時間戳都顯得很舊）。拋錯、非數字、`NaN`、`Infinity`：不寫 `u`、不掃描，所以什麼都不回收。常數不晚於既有時間戳：沒有東西過期。時鐘往前跳超過期限（假計時器、設在未來的常數、系統時間跳動）：另一個呼叫建槽時會把仍在使用的槽也刪掉，這是機制本身的限制，不是可以測掉的缺陷，規格如實寫出（「A clock that moves forward」）。後果：`js` 各路徑與分塊讀取失敗關閉；自己擁有槽的 `get text`／`get html`／`snapshot`／`exec` 在「存入」與「讀長度」之間遇到時維持既有行為（回空結果、結束碼 0，頁面在那一刻被替換時也是如此，`#76 INVARIANT`；另開 issue 追蹤）。

**D6：`u` 的更新放進每一個讀取腳本，輸出位元不變。** `lengthScript`、`errorScript`、`progressScript`、`readScript` 各在既有的 `var s = …` 之後加 `touchStatement`（在 `try` 裡取時鐘，讀得到才寫 `s.u`，讀不到就保留原本的時間戳）。建立點寫 `stampExpression`（讀不到就是 `undefined`，該槽永不回收）。回傳值與 `readScript` 的拒絕條件（槽被換掉或長度不符回空）不變。

**D7：不動 `cleanupScript` 與 CLI 端的清除流程。** 盡力刪除仍是第一道；回收只處理它沒做到的。

**D8：時鐘用 `Date.now()`，不用 `performance.now()`。** `performance.now()` 是單調的、以文件為單位（導頁歸零，與槽同壽命），不受系統時間調整影響，也許在機器睡眠時暫停。沒有採用：這些性質在 Safari 上沒有驗證（睡眠時是否暫停尚不知道），而假計時器通常兩個一起換掉，頁面撥時鐘的風險不變；風險是前跳超過 10 分鐘，後果失敗關閉並已寫進規格。若之後在真機上驗證了睡眠與導頁的行為，這是值得重新比較的選項。

**替代方案**（皆已拒絕，理由在 proposal Non-Goals）：頁面內計時器、CLI 日誌、前綴全刪、筆數上限。

## Risks / Trade-offs

- 停滯超過 10 分鐘的呼叫可能失敗（失敗關閉）。
- 掃描走訪 `Object.keys(window)`，全域屬性數千個的頁面約毫秒級；只在建立大型結果槽時發生，一般 `js` 不受影響。真機量測：見 tasks 3.4。
- 一個頁面自己有以 `__sbr_` 開頭、物件值、數字 `u` 的屬性會被當成孤兒：前綴是本 CLI 的約定，已在規格寫明。
- 孤兒槽的內容在被回收前，頁面上的任何指令碼都讀得到（槽名不是祕密，#190）；這個變更縮短它留存的時間，不改變誰讀得到。
- 掃描也會跑在 `get text`／`get html`／`snapshot` 後備／`exec` 步驟（它們共用 `storeScript`），成本同上（真機約 0.095 ms @ 約 5,200 個 `window` 屬性，0.010 ms @ 215 個；JavaScriptCore 約 0.12 ms @ 5,000）。
- 與 #259（PR #271）同動 `JSWrapper.inlineTail`：#259 改了該函式字串上方緊鄰的兩行說明文字，本變更改字串那一行，相鄰的修改在合併時會衝突；另外兩個 PR 都在 `CHANGELOG.md` 的開頭加條目、都改了 `CLAUDE.md` 的同一條。試合併實測 `JSWrapper.swift`、`CHANGELOG.md`、`CLAUDE.md` 三處衝突，內容都是機械性的：保留 #259 的說明文字與本變更的字串行。
- 規格中「The wrappers do not hide page globals」情境提到內嵌包裝仍遮住 `r`、`m`（#259 之前的事實）；#259 合併後該句要改，本變更逐字保留它，不替 #259 作主。

## Migration Plan

沒有遷移：新舊 CLI 互相容忍。舊版 CLI 建的槽沒有 `u`，新版掃描不動它；新版建的槽有 `u`，舊版 CLI 不認識它，讀寫其他欄位不受影響。
