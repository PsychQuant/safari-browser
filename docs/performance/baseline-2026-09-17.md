# Initial measurement baseline (#167)

Measured on 2026-09-17 with a debug build, Darwin 26A428, arm64. Each scenario
has 2 warmups and 5 measured samples, with separate timing-off/on runs. OS
caches were not flushed. The [raw report](baseline-2026-09-17.json) contains the
binary digest, both modes, trace records, failures and skips.

This preserves the original `b78a995` measurement snapshot. Later review repairs
add error-response timing and strengthen benchmark routing/readiness/cleanup;
these numbers are not measurements of those later revisions. No successful
live warm-daemon samples were recorded in this baseline.
That version did not validate daemon status stdout against the owned PID.
Its success counts retain the original tool's classification; they do not replace
the stricter status and host-liveness verification in later revisions.

Timing-off observations (milliseconds; nearest-rank successful samples):

| Scenario | p50 ms | p95 ms | Success / failure |
|---|---:|---:|---:|
| `startup.fresh-process-help` | 10.54 | 11.26 | 5 / 0 |
| `wait.fresh-process` | 20.31 | 21.63 | 5 / 0 |
| `exec.fresh-process-wait-batch` | 83.15 | 89.61 | 5 / 0 |
| `daemon.cold-host-status-including-startup` | 43.07 | 44.25 | 5 / 0 |
| `daemon.warm-host-fresh-cli-status` | 16.52 | 17.12 | 5 / 0 |
| `mcp.cold-host-wait-including-startup` | 202.91 | 207.71 | 5 / 0 |
| `mcp.warm-host-fresh-worker` | 23.54 | 34.26 | 5 / 0 |

All 70 measured non-GUI samples across both modes succeeded. The 8 GUI rows
(4 scenarios × 2 modes) were explicitly skipped: the host GUI was locked, so no
fixture was opened. Their null quantiles are not zero-cost successes.

These small-sample values are a baseline, not a speedup claim or a CI threshold.
Warm MCP retains the host but still creates a CLI worker. Daemon status measures
lifecycle/transport and does not establish AppleScript compilation savings. The
exec wait batch uses the subprocess dispatcher, not the in-process daemon route.

The previous roughly 10-second upload observation was a different, monitored
native-UI workload on the #101 branch. It cannot be compared directly with these
zero-wait queries. The present data shows that fresh CLI/worker overhead is in
the millisecond range for these workloads; actual Safari/AX/AppleScript phases
still require the owned live fixture or #101 acceptance environment.

Timing mode has overhead; see both modes before interpreting differences. For
example, the small warm-MCP samples vary between runs, so subtracting two medians
is not a stable estimate of instrumentation cost. The measurement tool itself
was corrected to avoid a 50ms exit-polling floor; that correction is not a
safari-browser performance improvement.
